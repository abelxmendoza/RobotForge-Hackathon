The workflow

Five steps from an idea to a verdict.

Every robot goes through the same path. Nothing downstream trusts the step before it: the model's spec is checked, and the twin is measured.

  1. 01

    Input

    Plain words, a pasted parts list, or a photo.

  2. 02

    Spec

    Muse Spark drafts a strict, structured hardware spec.

  3. 03

    Checks

    Engineering checks catch impossible or inconsistent numbers.

  4. 04

    Twin & gate

    The twin drives 1 m and turns 90° in Gazebo, graded on ground truth.

  5. 05

    Outputs

    URDF, a printable take-apart kit, and what's missing to buy.

What a PASS proves

  • The spec's numbers are consistent with each other: geometry, mass budget, voltages.
  • A twin built from exactly that spec drives 1 m and turns 90° within the locked thresholds.
  • The twin's own odometry agrees with simulator ground truth, so its sensors aren't lying to it.

What it doesn't prove

  • That a physical robot will behave the same. The gate tests the spec's simulated twin, not hardware.
  • That a photo-drafted spec is accurate. Photo dimensions are marked ESTIMATED until measured.
  • Anything beyond drive and turn. Other behaviours aren't gated yet.
Meta model

Muse Spark drafts the spec

Through the Meta Model API in Standard mode. It turns words or a photo into a strict spec schema and never writes simulation code.

Cross-check

SAM 3.1 double-checks photos

It locates parts in the picture independently. When it disagrees with Spark, both answers are printed, not smoothed over.

Gate

Ground truth, not belief

Drive and turn are judged against the simulator's true pose. Odometry is graded too, so a robot can't pass on its own word.

Run it yourself

Python, zero required dependencies for the core
pip install -e .
robotforge describe "a four-wheel rover, 30 cm long, with a front ultrasonic sensor" --mock --out rover.json
robotforge validate rover.json
robotforge urdf rover.json --out build/rover.urdf
robotforge run-gate rover.json
