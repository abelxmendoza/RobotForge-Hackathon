# Engineering verification audit — 2026-10-29

Scope: source review of `validate.py`, `harness.py`, `urdf.py`, `describe.py`, and `docs/DESIGN.md`. This is **not** a completed test execution or simulation validation.

## P0 — Electrical checks need power-path semantics

`validate.py` compares nominal motor voltage against nominal battery voltage with fixed ratios. This does not model a regulator, boost converter, motor driver, battery operating range, or allowable motor input range. It may reject feasible regulated designs and overlook other incompatible configurations.

**Acceptance:** Add explicit supply-path/driver metadata or label this a *direct-supply heuristic*; don't claim definitive electrical compatibility without the actual power path. Add tests for direct battery drive, buck conversion, boost conversion, and unknown driver.

## P0 — Simulation verdict scope

A Gazebo motion-gate PASS establishes the configured model met the configured trajectory thresholds; it does not validate the physical robot or prove torque, traction, inertia, or mass parameters are measured.

**Acceptance:** Attach parameter provenance (measured / datasheet / estimated / assumed), Gazebo version, timestep, input spec hash, and motion report to every gate artifact. Clearly label unsupported parameters and distinguish simulated PASS from hardware validation.

## P1 — Harness graph and numeric validity

`harness.py` recursively aggregates current across power edges. Branching, shared downstream nodes, cycles, and multiple sources need explicit semantics to prevent incorrect rail budgets. `_num` accepts finite negative values; voltage-drop computation uses a zero percent result when volts <= 0, which can conceal invalid input.

**Acceptance:** Validate current >= 0, cable length >= 0, supply voltage > 0, and physically meaningful AWG; report invalid values as ERROR or NOT_CHECKED rather than silently passing. Test diamond-shaped graphs, loops, parallel supplies, and unknown loads.

## P1 — Geometry / collision consistency

`validate.py` treats wheel radius versus declared clearance as an absolute impossibility, although its validity depends on the chassis layout. The check does not inspect the generated collision geometry.

**Acceptance:** State the assumed conventional wheel-on-ground chassis configuration; cross-check wheel contact plane, chassis collision bottom, and declared clearance in the generated model.

## P1 — End-to-end reproducibility

**Acceptance:** Run unit tests and a clean-environment headless Gazebo gate in CI; preserve command, dependency versions, random seed, inputs, outputs, and artifact hashes. Add a deliberately invalid spec that is rejected and a repaired spec that passes. Avoid claims of executed tests until CI confirms them.

## P2 — Muse Spark repair demonstration

Use Muse Spark to propose bounded spec repairs, not to assign pass/fail verdicts. Validate every revision with deterministic checks, enforce a retry limit, record before/after diffs, and require human approval for assumptions involving safety-critical electrical or mechanical choices.
