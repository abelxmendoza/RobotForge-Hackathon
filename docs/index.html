01 — The Pipeline

Words in. A measured robot out.

Five stages, each one checkable. Nothing moves to the next stage on a model's say-so — the spec is validated as engineering, and the finished twin is validated as motion.

STEP 1

Describe

You describe the robot you want in plain language — size, wheels, drivetrain, sensors, job to do.

STEP 2

Spec

Muse Spark, via the Meta Model API, converts the description into a structured robot spec — a JSON document, not a vibe.

STEP 3

Validate

The spec is checked as engineering: dimensions, masses, and component consistency must hold together before anything is built.

STEP 4

Twin

The validated spec becomes URDF/SDF and a digital twin in Gazebo Sim (Harmonic), running headless.

STEP 5

Gate

The twin drives 1 m and turns 90°. DiffDrive odometry measures what it actually did, and the gate grades it against fixed thresholds.

02 — Why Verification Matters

A generated robot is a claim. The gate checks it.

Language models are good at producing robot designs that read correctly. Reading correctly is not the same as moving correctly. RobotForge's core bet is that generation is only half the product — the other half is a measurement with published thresholds, applied the same way every time, that a design can genuinely fail.

How the gate works

The twin is commanded through two maneuvers: drive 1 meter, then turn 90 degrees. DiffDrive odometry from the simulator is the measurement source — the grade comes from where the robot actually ended up, not from what it was told to do.

The thresholds are fixed in advance and do not move to fit a result. Between pass and fail sits an explicit marginal band, so borderline physics reads as borderline — not as a quiet pass.

Grading thresholds

CheckPassMarginalFail
Distance error≤ 5%5–10%> 10%
Heading error≤ 5°5–10°> 10°

Distance error is measured against the commanded 1 m drive; heading error against the commanded 90° turn.

03 — Live Status

Where it actually stands — Oct 26, 2026

Day one of the build window. This section reports what has been run and measured, including the parts that don't flatter the project.

LIVE

Natural-language describe — running on Muse Spark

The describe stage runs live against muse-spark-1.3 through the Meta Model API — not a mock. The first live, model-generated spec (examples/pathfinder-live.json, in the repo next to the hand-authored examples/pathfinder.json) passed all engineering validation checks with zero errors and zero warnings.

REAL RUNS

The motion gate executes in Gazebo — and issues real verdicts

The twin runs headless in Gazebo Sim (Harmonic) on a real Linux host, drives the maneuvers, and is graded from measured odometry. The gate is not a demo script: it returns pass, marginal, or fail based on the numbers above.

GATE: FAIL

Current verdict: FAIL — and we know why

Current gate verdicts are FAIL: the twin overshoots its targets. The root cause has been measured, not guessed — command-transport latency in the test harness (getting drive/stop commands into the simulator) lets the robot travel past the mark before the stop lands. The fix is in progress.

The gate measures instead of assuming. A verification tool that flatters the thing it verifies would be worthless — so the FAIL stays on this page until the measured numbers earn a different verdict.
04 — Hackathon & Provenance

Built in the window, on the record.

RobotForge was built fresh during the Meta Global AI Developer Hackathon, October 26 – November 4, 2026 — Indie track, theme “Push the Frontier.”

Provenance

All demo code in the repository was written inside the hackathon window. Pre-existing design exploration informed the architecture — the idea was thought through before the window opened — but the code that runs was built during the event, in the open, commit by commit.

Under the hood

The core is zero-dependency Python: specs are JSON, generation produces URDF/SDF, and the twin runs headless Gazebo with DiffDrive odometry as the single measurement source. The only hosted service in the loop is the Meta Model API, for the describe stage.
